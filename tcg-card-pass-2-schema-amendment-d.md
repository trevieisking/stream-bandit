# CP2-03D-01 — Declarative continuous modifiers

The base schema already reserves `continuous` arrays for Essence and Tactics and permits a Creature Ability to use `mode = continuous`. This amendment defines how continuous rules are represented and evaluated.

A continuous modifier is declarative state, not a repeatedly-created temporary effect:

```json
{
  "id": "continuous-id",
  "kind": "attack_damage | incoming_attack_damage | damage_packet_amount | withdrawal | attack_cost",
  "target": "$source_creature",
  "when": {
    "predicate": "source_has_condition",
    "condition": "Scorched"
  },
  "amount": -10,
  "filters": {
    "damage_scope": "attack",
    "source_controller": "opponent"
  }
}
```

## Continuous evaluation contract

1. A continuous modifier exists only while its source card/attachment is legally present and active.
2. The engine evaluates `when` against the authoritative state at the moment the affected rule value is needed.
3. A continuous modifier does **not** create a new stored modifier on every state change; therefore state oscillation cannot duplicate or stack one card instance with itself.
4. Separate legal card instances remain separate sources and may stack unless a global/card rule explicitly says otherwise.
5. If `when` becomes false, that source contributes nothing immediately; no cleanup event is required.
6. Continuous attack-damage modifiers enter the attacker-side modifier stage before Weakness.
7. Continuous incoming-attack modifiers enter the defender-side prevention/reduction stage after Weakness and any explicit rare Resistance, before Shield.
8. Continuous `damage_packet_amount` modifiers apply only to damage packets matching their filters and are not attack Weakness/Resistance rules.
9. The source card uid + continuous id forms the stable identity for replay, ordering and debugging.

## Conditional value form

A continuous modifier may use a deterministic value expression when the amount is not constant:

```json
{
  "value": {
    "default": 10,
    "cases": [
      {
        "when": {"predicate": "target_printed_hp_at_least", "value": 200},
        "amount": 20
      }
    ]
  }
}
```

Cases are evaluated in written order; the first matching case wins. `value` and a scalar `amount` are mutually exclusive.

This supports rules such as a Relic granting +10 attack damage, or +20 instead for a 200+ printed-HP creature, without installing card-name code.

# CP2-03D-02 — Typed damage packets

Non-attack damage must carry its cause so cards can modify exactly the intended damage without accidentally changing unrelated damage.

Every damage application is represented internally as a damage packet. The minimum canonical payload is:

```json
{
  "packet_id": "damage-seq-id",
  "damage_class": "attack | recoil | condition | effect",
  "amount": 20,
  "target_uid": "creature-instance-uid",
  "source_card_uid": "source-instance-uid",
  "source_action_id": "action-id",
  "source_controller_seat": 1,
  "source_attack_id": null,
  "condition": null,
  "preventable": true
}
```

## Damage classes

- `attack` — normal attack damage. It uses the full attack pipeline, including Weakness and any explicit rare Resistance.
- `recoil` — damage placed on a creature because of its own attack or an effect explicitly defined as attack recoil. It is **not** multiplied by Weakness.
- `condition` — damage generated by a global condition rule, such as Scorched or Venomed. It is **not** multiplied by Weakness.
- `effect` — direct damage from an Ability, Device, Relic, Realm or other non-attack instruction. It is **not** multiplied by Weakness.

`source_attack_id` is present for `attack` and for attack-owned `recoil` where appropriate. `condition` is present for condition damage.

## Damage packet events

Add canonical events:

- `before_damage_packet`
- `after_damage_packet`

`before_damage_packet` occurs after the packet's base amount/cause is known but before that packet is finally applied. Packet-specific legal modifiers may change the current amount there.

`after_damage_packet` records the final amount actually placed after reductions/prevention. Zero is a valid final amount.

Attack packets still obey the base attack-damage ordering. These generic events do not move Weakness or Shield to a different stage.

# CP2-03D-03 — Direct/recoil damage operation

Extend `DIRECT_DAMAGE` so every structured non-condition damage instruction declares its class:

```json
{
  "op": "DIRECT_DAMAGE",
  "target": "$source_creature",
  "amount": 20,
  "damage_class": "recoil",
  "source_attack_id": "meltline-charge"
}
```

or:

```json
{
  "op": "DIRECT_DAMAGE",
  "target": "$target",
  "amount": 20,
  "damage_class": "effect"
}
```

The global condition owner creates `damage_class = condition` packets itself; card definitions do not reproduce the entire Scorched/Venomed timing rule.

A v0.2 definition must never omit `damage_class` from `DIRECT_DAMAGE`.

# CP2-03D-04 — Modify the current damage packet

Add operation:

```json
{
  "op": "MODIFY_CURRENT_DAMAGE_PACKET",
  "delta": -10,
  "minimum": 0
}
```

Semantics:

1. legal only while resolving `before_damage_packet` for a packet already in context;
2. modifies only that packet instance;
3. cannot change the packet's class/source/target;
4. packet amount cannot fall below the specified minimum, normally 0;
5. multiple legal modifiers apply in deterministic listener/source order;
6. the event log records the source of each modification and the pre/post amounts.

A listener can filter packets generically, for example:

```json
{
  "event": "before_damage_packet",
  "requirements": {
    "any": [
      {"predicate":"damage_packet_class_is","damage_class":"recoil"},
      {"all":[
        {"predicate":"damage_packet_class_is","damage_class":"condition"},
        {"predicate":"damage_packet_condition_is","condition":"Scorched"}
      ]}
    ]
  },
  "limit":{"scope":"turn","count":1,"owner":"card_instance"},
  "steps":[{"op":"MODIFY_CURRENT_DAMAGE_PACKET","delta":-10,"minimum":0}]
}
```

This is the generic basis for effects that protect only against recoil/Scorched damage.

# CP2-03D-06 — Current-attack declaration context

  "source_creature_uid": "instance-uid",
  "source_controller_seat": 1,
  "target_creature_uid": "instance-uid",

Add predicates:

- `event_attack_source_damaged`
- `event_attack_source_element_is`
- `event_attack_target_has_condition`

The attack event context is server-authoritative and does not expose hidden information.

# CP2-03D-07 — Modify the current attack's attacker-side damage

Add operation:

```json
{
  "op": "MODIFY_CURRENT_ATTACK_DAMAGE",
  "delta": 20
}
```

Semantics:

1. legal only while resolving an `attack_declared`/attack-build listener for the current legal attack;
2. changes that attack action's attacker-side damage modifier, not the printed card definition;
3. enters the attack pipeline **before Weakness ×2**;
4. does not persist to a later attack unless another structured rule creates a temporary modifier;
5. source card/listener attribution is recorded in the attack event log.

This supports continuous/triggered named Abilities such as “the first attack this creature declares this turn gets +20 if it is damaged” without an attack-name string parser.

## Listener-limit consumption

When a listener has a `limit`, that use is consumed when the listener legally triggers and enters the trigger snapshot, before its `IF`/steps resolve. A later false conditional inside that triggered item does not allow the same source to trigger again on a second event during the same limit window.

This makes “the first attack this creature declares during your turn” deterministic even when the bonus itself is conditional.

# CP2-03D-08 — One-shot next-attack modifier with completion rider

Extend a temporary attack modifier with optional action-bound completion steps:

```json
{
  "op": "ADD_ATTACK_DAMAGE_MODIFIER",
  "target": "$target",
  "amount": 30,
  "duration": {
    "expires_on": ["end_of_turn"],
    "max_uses": 1,
    "consume_on": "legal_attack_declared"
  },
  "on_consume": {
    "bind_to_consuming_action": true,
    "timing": "after_attack_effects_before_defeat_scan",
    "steps": [
      {"op":"DIRECT_DAMAGE","target":"$modifier_target","amount":20,"damage_class":"effect"}
    ]
  }
}
```

## Rider contract

1. If no legal attack consumes the modifier before expiry, the modifier and rider expire together.
2. A legal declaration consumes the one use and binds the rider to that exact attack action.
3. The rider resolves after the consuming attack's own `after_damage` instructions but **before the final defeat/Reward/win scan for that complete attack action**.
4. The rider still resolves if the attack's damage was prevented or reduced to zero, because the legal attack consumed the modifier.
5. If the bound target is no longer a legal in-play creature at rider timing, the rider fails closed for that target rather than retargeting.
6. A bound rider is mandatory unless its nested steps explicitly contain an `OPTIONAL` choice.
7. The event log records the modifier source, consuming attack action and rider result.

This supplies the generic lifecycle for “next attack gets a bonus; after that attack, damage the same creature” without a Mythic/card-id exception.

# CP2-03D-09 — Active-seat event predicate

Add predicate:

```json
{
  "predicate": "event_controller_is_active_seat"
}
```

It is true only when the controller represented by the current event equals the match's active seat for that turn.

This differs from merely checking `controller = self` on a symmetrical Realm. It prevents an inactive player's forced promotion during the active player's attack turn from receiving an “on your own turn” Vanguard-entry bonus that cannot sensibly be used.

Also permit:

```json
{"predicate":"event_controller_is_not_active_seat"}
```

for future rules that explicitly care about off-turn events.

# CP2-03D-10 — Generic counted-card query in damage formulas

The base schema defines `count_add`. This amendment defines a data-driven counter query so formulas do not require phrases such as “friendly damaged creature.”

Example:

```json
{
  "damage_formula": {
    "base": 160,
    "terms": [
      {
        "kind": "count_add",
        "counter": {
          "kind": "count_cards",
          "controller": "self",
          "zone": "field",
          "filters": {
            "card_family": "Creature",
            "damaged": true
          }
        },
        "amount_per": 10,
        "max_count": 4
      }
    ]
  }
}
```

Rules:

1. the count is snapshotted at the formula timing specified by the attack, normally legal declaration when the accepted wording says “when this attack is declared”;
2. the source creature is naturally included if it occupies the counted zone and satisfies the filters;
3. `max_count` caps only the count contribution, not the existence of additional matching cards;
4. all filters use ordinary structured selectors/predicates;
5. hidden zones cannot be counted unless the card explicitly authorizes that information and the rules define the visibility consequence.

This counter query is generic for future formulas involving friendly/ opposing creatures, damaged state, stage, element, traits or other public field properties.

# CP2-03D-11 — Continuous attack modifier examples

These examples are schema demonstrations, not new card-design authority.

## While source is damaged, one named attack gets +10

```json
{
  "id":"example-warm-blood",
  "kind":"attack_damage",
  "target":"$source_creature",
  "when":{"predicate":"source_damaged"},
  "amount":10,
  "filters":{"attack_id":"example-attack-id"}
}
```

## While source is Scorched, opposing attack damage received is reduced by 10

```json
{
  "id":"example-furnace-hide",
  "kind":"incoming_attack_damage",
  "target":"$source_creature",
  "when":{"predicate":"source_has_condition","condition":"Scorched"},
  "amount":-10,
  "filters":{"source_controller":"opponent"}
}
```

## Attached creature attacks +10, or +20 instead at printed HP >= 200

```json
{
  "id":"example-cinder-charm",
  "kind":"attack_damage",
  "target":"$attached_creature",
  "when":{"predicate":"target_element_is","element":"Ember"},
  "value":{"default":10,"cases":[{"when":{"predicate":"target_printed_hp_at_least","value":200},"amount":20}]}
}
```

# CP2-03D-12 — Condition-damage modification example

A Special Essence that makes Scorched more dangerous uses a persistent packet modifier rather than rewriting the global Scorched rule:

```json
{
  "id":"example-scorched-risk",
  "kind":"damage_packet_amount",
  "target":"$attached_creature",
  "when":{"predicate":"target_has_condition","condition":"Scorched"},
  "amount":10,
  "filters":{"damage_class":"condition","condition":"Scorched","target":"attached_creature"}
}
```

The global Scorched owner still schedules the ordinary Scorched packet and recovery check. The attached card changes only that packet's amount while its own condition/source requirements remain true.

# CP2-03D-13 — Validation additions

A v0.2 validator must additionally reject:

1. a continuous modifier whose `kind`, target or filter combination is unsupported;
2. a continuous modifier that attempts to persist by creating duplicate stored modifiers on state refresh;
3. a `DIRECT_DAMAGE` instruction without explicit `damage_class`;
4. a non-attack damage packet attempting to use Weakness or Resistance automatically;
5. `MODIFY_CURRENT_DAMAGE_PACKET` outside `before_damage_packet` context;
6. packet predicates outside a valid packet context;
7. `MODIFY_CURRENT_ATTACK_DAMAGE` outside the current attack-build/declaration context;
8. a current-attack listener that references an unknown attack id;
9. an action-bound completion rider without a deterministic consuming event and expiry;
10. a rider that retargets silently when its bound target is gone;
11. a counted-card damage formula using a hidden zone without explicit visibility authorization;
12. an unsupported `event_controller_is_active_seat` context;
13. a scalar `amount` and conditional `value` supplied simultaneously on one continuous modifier;
14. a use-limited attack listener whose limit consumption timing is ambiguous.
